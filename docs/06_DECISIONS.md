1. README와 PRD를 읽고 D-001~006을 순서대로 시작한다.

최초 계획 문서 작성 시점에 수행한 것은 프로젝트 확인, 공식 기술/비용 조사, 계획 문서 작성이었다. 이후 진행 사항은 아래 후속 기록과 docs/11_CHAT_HANDOFF.md를 따른다.

## ADR-N01 · 백엔드 계획 변경 / 2026-09-26

사용자가 TypeScript·NestJS를 가장 많이 사용했고 Python은 조금 사용했다고 확인했다. 백엔드를 NestJS로 정하고 Java/C# 신규 학습은 출시 계획에서 제외한다. 기존 v0.1의 브라우저→Supabase 업무 조회/RPC와 Edge Functions 중심 설계를 대체한다.

업무 API·권한·트랜잭션·외부 호출은 Nest, DB/인증은 Supabase, 화면은 React/Vite로 나눈다. Prisma는 ORM/migration 추천안이다. API 컨테이너 배포와 비용을 추가하고 인증/RLS 통합 시험을 기반 작업에 포함한다. Python은 필요할 때 오프라인 데이터 실험에 사용하며 별도 서버 추가는 실제 요구 확인 후 결정한다.

당시 변경은 계획 v0.2였다. 제품의 v0/v0.1 범위와 베타 목표는 유지한다. 공수는 Nest 경험이 확정되었다고 임의로 줄이지 않고, 프론트 학습과 API 운영/RLS 검증을 포함해 첫 2주 후 다시 산정한다. API/DB 접근 기반이 추정을 넘으면 기능 범위와 일정을 함께 조정한다. 이 변경은 앱 구현이나 클라우드 계약 완료를 뜻하지 않는다.

## 2026-09-26 · v0.3 공식 문서/CLI 개발 원칙

사용자가 React + Vite / NestJS, 터미널 설치·생성·검증, 공식 문서 확인, PostgreSQL·Redis·Compose·모듈화를 포함한 DevOps 검토를 확정했다.

로컬 개발은 Compose PostgreSQL을 기본으로 하고 Redis를 cache profile로 선택한다. Supabase Auth/관리형 운영 구성은 인증 단계에서 결정한다. 공식 필수 조건과 프로젝트 선택을 구분한다. Dayjoin에서 기반을 먼저 검증하고 Cashjoin·Workjoin은 같은 원칙을 적용한 계획 상태로 유지한다.

## 후속 확정 · 세 프로젝트 기초 세팅 후 새 채팅

사용자가 세 프로젝트 모두 기초 세팅까지만 완료하고 각 프로젝트의 새 채팅에서 하나씩 진행하기로 정했다. 공통 기반·독립 포트/DB/volume·빌드/연결 검증을 완료했다. 인증·제품 기능은 이번 범위에서 시작하지 않는다. 현재 상태와 다음 후보는 docs/11_CHAT_HANDOFF.md가 기준이다.

## ADR-D04 · 첫 사용 대상 / 2026-09-26

사용자는 가족·커플이 첫 사용 대상에 가깝고, 이후 친구·모임·스터디·동호회에서도 사용한다고 확정했다. 첫 화면의 예시와 사용성 확인은 가족·커플의 일정에 맞춘다.

프로젝트 설계 선택: 기존 그룹·멤버·일정 구조와 owner/editor/viewer 역할을 유지한다. 관계별 전용 스키마나 필수 그룹 유형 선택을 추가하지 않는다. 특정 관계에 맞춘 기능은 실제 필요가 확인되면 별도 백로그로 판단한다. 이 기록은 사용자 선택과 프로젝트 설계 결정이며 새로운 기술의 공식 필수 조건을 뜻하지 않는다.

사용자는 우선 공유할 일정으로 저녁식사와 여행을 제시했다. 기존 D-001의 사례 3개 계획을 조정해 이 두 사례로 화면 설계를 시작한다. 시간 지정 식사와 여러 날짜에 걸친 여행은 이를 구체화한 설계 초안이다. 별도 필수 일정 유형 필드나 전용 폼 없이 기존 제목·시작/종료·종일·메모·대상 캘린더로 표현한다.

실제 사용성은 아직 검증하지 않았으며 첫 시험 그룹의 구성·규모는 실제 공유 시험 전에 확인한다. 다음 작업은 D-002의 목록·입력·초대 화면 흐름 정리다. 이번 변경은 요구사항 문서 정리이며 제품 기능 구현은 포함하지 않는다.

## ADR-D05 · 모바일 첫 화면 흐름 / 2026-09-26

사용자의 다음 단계 진행 요청에 따라 D-002 설계 산출물을 작성했다. [화면 흐름 문서](12_SCREEN_FLOWS.md)에 목록·입력·초대·수락의 구조와 상태를 기록했다.

프로젝트 설계 선택: 모바일은 날짜순 목록과 전체 화면 입력으로 시작한다. 저장 대상과 공유 범위를 명시하고, 저녁식사/여행을 공통 폼으로 표현한다. 종일 여행의 종료 날짜는 화면상 포함으로 안내하며 API 저장 표현과의 매핑은 일정 모델 단계에서 검증한다. 초대 권한은 editor/viewer, 발급·회수는 owner로 기존 PRD를 유지한다.

미리보기 동작과 반응형 배치는 확인했지만 인증·영속 저장·권한 경계·사용성은 구현 또는 검증하지 않았다. 다음 구현은 D-003~006의 React 가상 일정 목록·입력 폼이며 실제 공유 기능은 권한 기반 후에 연결한다. 공식 접근성 가이드와 프로젝트 선택의 구분, 확인 날짜와 검증 한계는 화면 흐름 문서에 기록했다.

## ADR-D06 · 따뜻한 화면 디자인 / 2026-09-26

사용자는 최근 UI처럼 다듬되 초록색을 고정할 필요는 없다고 했고, 제시한 방향 중 **부드럽고 따뜻한 색감 + 둥근 화면**을 선택했다. 초기 녹색 와이어프레임의 시각 방향을 대체한다.

프로젝트 제안: 아이보리·브라운 바탕, 살구색 주요 동작, 둥근 일정 행, 큰 날짜와 명확한 제목, 적은 구분선. 다크 모드는 따뜻한 차콜로 대응한다. 색상의 정확한 값이나 최종 브랜드 승인은 아직 확정하지 않았다. 최근 Linear 디자인 개편과 Notion Calendar를 참고한 근거는 [화면 흐름 문서](12_SCREEN_FLOWS.md)에 기록한다. 제품 기능 범위와 역할 모델은 유지하며 이번 변경은 D-002 미리보기 수정이다.

## ADR-D07 · 일정·가계부 통합 등록 방향 / 2026-09-26

사용자는 등록할 종류를 일정/가계부로 선택하고, 기록별로 같은 캘린더 구성원에게 공유하거나 본인만 보는 방식과 색상 구분을 제안했다. [통합 등록 설계안](13_CALENDAR_RECORDS_PROPOSAL.md)을 다음 화면 설계의 기준으로 추가했다.

이전의 가계부 별도 진행 권고는 Cashjoin의 계좌·카드·이체까지 포함한 범위를 전제로 했다. Dayjoin의 통합 화면에서 수동 수입·지출 기록을 제공하는 방향은 가능하며, 초기 가계부 범위·공개 기본값·색상 매핑·수정 권한은 설계 제안으로 구분한다. 개인 작업 공간 격리는 유지하고 통합 화면에서 개인/공유 내역을 함께 표시하는 구성을 우선 검토한다. Cashjoin 저장소·DB·Auth·배포를 합치거나 중단하는 결정은 하지 않았다.

기존 일정 중심 PRD·백로그·미리보기는 이전 범위다. 새 방향의 화면과 상세 인수 조건은 아직 구현하지 않았으며 완료 체크나 기존 공수를 확대 적용하지 않는다.

## ADR-D08 · 계좌·카드·이체를 포함한 통합 가계부 / 2026-09-26

사용자는 계좌·카드·이체를 포함한 가계부도 가능하다고 명시했다. Dayjoin의 가계부 범위를 단순 수입·지출 기록으로 제한했던 제안을 대체하고, 개인 금융 계정과 잔액·신용카드 사용/납부·내부 이체·수정/취소/환불까지 통합 제품 요구사항에 반영했다. PRD의 DJ-F01~08, 백로그 F-001~060과 [확장 설계안](13_CALENDAR_RECORDS_PROPOSAL.md)이 현재 기준이다.

프로젝트 제안: 원화 수동 등록부터 구현하며 개인 원장과 캘린더에 공개하는 거래 정보를 구분한다. 공유 범위를 바꿔도 원장 소유권·잔액은 바뀌지 않고, 캘린더 구성원이 다른 사람의 계좌 잔액·미공유 거래를 조회하거나 수정하지 못한다. 내부 이체와 카드 납부를 지출로 중복 집계하지 않는다. 금융기관 자동 연동·송금 실행·공동 계좌 권한은 이번 요청으로 확정하지 않는다.

계좌·카드·이체는 통합 제품에 포함하고 구현 순서는 계정/원장 → 수입·지출/카드 사용 → 이체·납부/정정 → 공유 조회로 나눈다. 이 순서는 기능 제외나 Cashjoin으로의 이관이 아니다. 기존 Cashjoin 기획은 참고했고 해당 저장소는 변경하지 않았다. 서비스의 DB·Auth·배포 독립 원칙도 유지한다.

이번 변경은 문서·백로그 갱신이다. UI/원장/schema/권한은 미구현이며 기존 일정 베타 공수는 통합 범위에 사용할 수 없다. 다음 작업은 F-001 통합 시안이다.

## F-001 통합 시안 작성 · 2026-09-26

후속 진행 요청에 따라 통합 등록, 계좌·카드, 월 합계와 개인/공유 관점의 대화형 시안을 작성했다. 이전 일정 시안을 보존했다. 새 시안에서 계산한 가상 잔액과 공개 화면, 오류 복구 및 66개 반응형 조합을 확인했다. 발견한 설정 복원에 따른 상세 화면 이탈을 수정하고 빠른 전환과 입력 보존을 재확인했다.

산출물·실제 확인 결과·한계는 [F-001 기록](14_UNIFIED_SCREEN_PREVIEW.md)에 적었다. 금융 원장·DB/RLS·실제 공유는 미구현이다. 다음은 F-002 React 가상 데이터 화면이며 F-001 완료가 통합 제품 출시 완료를 의미하지 않는다.

## ADR-D09 · 월간 달력을 첫 화면의 중심으로 / 2026-09-26

사용자는 “처음부터 달력이 메인이면 좋을 것 같다”고 요청했다. 목록 중심의 초기 설계 선택을 변경해 월간 달력을 항상 펼쳐 놓고, 선택한 날짜의 기록과 등록 버튼을 그 아래에 배치한다. 계좌·카드와 월 합계는 보조 화면으로 유지한다. 종류/공개 범위 필터는 달력 아래에 두며 날짜 칸의 표시와 목록에 동일하게 적용한다.

등록 폼은 선택일로 시작하고 저장 후에도 해당 날짜로 돌아온다. 다른 멤버의 비공개 기록은 날짜 칸의 표시·건수에도 포함하지 않는다. 따뜻한 색감과 둥근 화면은 유지한다. 이는 사용자 피드백을 반영한 제품 설계이며 공식 프레임워크의 필수 구조가 아니다.

F-001 시안과 인계 기준에 반영했으며, 15개 추가 배치·날짜/월 이동·등록/저장·공개 표시·오류 복구를 확인했다. 실제 앱은 아직 공식 예제이고 다음 F-002에서 이 구성을 구현한다. 상세 근거·검증 한계는 [시안 기록](14_UNIFIED_SCREEN_PREVIEW.md)을 따른다.

## ADR-D10 · 모바일 앱과 웹 모두 제공 / 2026-09-26

사용자는 앱과 웹 버전을 모두 원한다. 기존 모바일 앱 제외 방침을 변경한다. 두 환경 모두 월간 달력이 중심이며 같은 Dayjoin 계정과 서버 데이터를 사용한다. 모바일은 터치·세로 배치, PC는 넓은 달력·선택일 상세의 병렬 배치를 제안한다.

기술 추천은 기존 React + Vite를 유지하고 Capacitor로 iOS/Android 앱을 구성하는 방식이다. 1인 개발에서 UI와 로직 재사용을 우선하는 판단이며, React Native + Expo도 대안이다. 사용자가 특정 모바일 프레임워크나 OS별 출시 순서를 확정한 것은 아니다. 앱과 웹의 인증 복귀·키보드·뒤로가기·배포는 각각 검증한다.

[앱·웹 계획](15_APP_AND_WEB_PLAN.md)에 공식 문서 근거/설치 버전/추천 구분과 개발 순서를 기록했다. PRD·백로그·인계에 반영했으며 실제 앱 생성·빌드·배포는 수행하지 않았다. 다음 F-002는 모바일/PC 배치를 함께 구현하고 첫 화면 이후 P-010으로 기기 검증한다.

## F-002 React 가상 화면 완료 · 2026-09-26

사용자의 후속 진행 요청으로 `apps/web`의 공식 예제를 통합 제품 화면으로 교체했다. FullCalendar 7.1.0과 React 19.3.0 호환 조건을 확인하고 공식 pnpm CLI로 필요한 패키지만 추가했다. 모바일 달력 아래/PC 오른쪽에 내역을 두며 공통 모달로 등록·수정한다. 필터는 달력 조작부에 배치해 날짜 표시와 목록을 함께 좁힌다.

입력·계산 로직을 컴포넌트에서 분리하고 원화 BigInt 계산, 개인/공유 표시, 카드 납부 중복 집계 방지와 환불 한도를 검사한다. 서버 미연결이며 이 계산과 가상 관점 전환을 보안 경계나 금융 원장 구현으로 간주하지 않는다. 새로고침하면 예시 데이터로 돌아간다.

웹 도메인 검사 17개와 API 기존 단위 6개, 전체 lint/typecheck, 웹 build가 통과했다. 15개 반응형 배치와 등록·수정·취소·환불/납부·오류 재시도·다른 멤버 상세·키보드 월 이동을 확인했다. 설치 근거와 실패/수정·검증 한계는 [F-002 기록](16_REACT_UI_IMPLEMENTATION.md)에 남겼다. P-010 앱 기기 검증이 다음이며 Capacitor/네이티브 프로젝트·실제 인증/원장·배포는 아직 없다. 이번 변경은 커밋·푸시하지 않았다.

## ADR-D11 · 라이브러리 우선 개발 / 2026-09-26

사용자는 공휴일 라이브러리를 검토한 뒤 앞으로 라이브러리로 가능한 부분은 최대한 라이브러리를 사용하기를 요청했다. 공통 기능은 기존 의존성 또는 적합한 라이브러리를 우선 사용하고, 직접 구현은 제품 고유 규칙이나 근거 있는 예외에 한정한다. 선정·버전·갱신·검증 기준을 AGENTS 및 [개발 기준](08_ENGINEERING_STANDARD.md)에 반영했다.

공휴일은 `@hyunbinseo/holidays-kr`를 우선 후보로 추천하며 세부 전환 순서와 한계는 [공휴일 문서](17_KOREAN_HOLIDAYS.md)에 기록했다. 사용자 확정 사항은 라이브러리 우선 원칙이고, 특정 패키지와 운영 API 연동은 프로젝트 제안이다. 이번 변경은 문서뿐이며 의존성 설치·공휴일 코드 교체·자동 갱신은 수행하지 않았다.

## ADR-D12 · 공휴일 패키지 적용 / 2026-09-26

사용자가 추천한 전환의 진행을 승인해 `@hyunbinseo/holidays-kr@5.2027.2`를 공식 pnpm CLI로 설치했다. 공개 `/all` export의 2018~2027년 데이터를 사용하며 직접 작성한 날짜 목록을 제거했다. 표시용 별칭과 지원 연도는 `holidays.ts`에서 관리하고, 한 날짜에 겹친 공휴일 이름을 보존한다. 모바일 이름 영역은 내용에 따라 늘어나도록 변경했다.

웹 테스트 26개·lint/typecheck/build, 기존 46개 날짜/표시 전수 일치, 320/360/768/1280px에서 긴 이름과 범위 밖 안내 검증을 완료했다. 데이터는 배포된 패키지 버전의 스냅샷이며 새 지정은 패키지 업데이트·검증·배포로 반영한다. 서버 API·자동 갱신·커밋·푸시는 이번에 추가하지 않았다. 공식 조건과 프로젝트 선택, 실패/수정, 실제 결과는 [공휴일 문서](17_KOREAN_HOLIDAYS.md)를 따른다.

## ADR-D14 · 웹앱(PWA) 우선으로 변경 / 2026-09-27

사용자는 앱 대신 웹앱으로 먼저 사용하기로 했다. ADR-D10의 앱·웹 동시 개발을 현재 범위에서 보류하고 React/Vite의 반응형 화면에 설치형 PWA를 적용한다. 기존 네이티브 코드는 feature/mobile-shell / Draft PR #4에 보존한다. 앱 재개나 스토어 출시는 별도 요청 후 판단한다.

라이브러리 선택은 vite-plugin-pwa/Workbox다. 공개 정적 화면만 캐시하고 업무 데이터·인증 응답은 캐시하지 않는다. 사용자 선택 업데이트와 다중 탭 입력 보호는 프로젝트 설계 결정이다. 예시 데이터의 새로고침 초기화는 유지하며 설치를 영속 저장 기능으로 표시하지 않는다. [구현 근거·검증](24_PWA_IMPLEMENTATION.md)과 [개발 순서](15_APP_AND_WEB_PLAN.md)를 따른다.
