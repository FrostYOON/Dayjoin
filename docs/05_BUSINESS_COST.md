# Dayjoin 수익화·비용

## 판매 가설

기본 일정 공유는 무료로 시험하고, 유료 주체는 개인 회원보다 **그룹 소유자**로 잡는다. 한 사람의 결제로 그 그룹 구성원이 혜택을 받게 하는 안이다. 처음부터 기능 수를 늘려 결제 이유를 만들지 않고, 반복 일정/리마인더가 실제로 필요한지 확인한다.

| 구분 | 가설 |
|---|---|
| 무료 | 작은 공유 그룹 1개, 기본 일정/변경 확인, 기본 내보내기 |
| 유료 후보 | 그룹 확장, 반복 일정/알림 고도화, 여러 캘린더 운영 편의 |
| 가격 시험 후보 | 그룹당 월 3,900원 또는 5,900원. 시장 근거가 없는 검증값이며 판매가 확정 아님 |
| 유입 실험 | 본인 사용→지인 5개 그룹 시험→그룹 초대 확산. 직접 연락/게시 전 대상과 메시지 별도 결정 |

정확한 그룹/멤버 제한은 실제 사용량과 인터뷰로 정한다. 기간이 지난 자기 데이터 열람/기본 내보내기를 결제 장벽으로 막지 않는다. 유료 해지 후 초과 그룹은 즉시 삭제하지 않고 읽기/정리 기간 정책을 설명한다.

4주 사용한 그룹의 담당자 5명에게 가장 도움이 된 순간·현재 대안·가격을 보여준 뒤 계속 쓸지를 확인한다. 2명 이상이 유료 시험에 동의하면 결제 개발의 근거로 삼되 실제 결제와 갱신으로 다시 검증한다. 초대율이 낮다면 결제 구현보다 온보딩 개선이 먼저다. 광고/AI 추천은 초기 수익 모델에 포함하지 않는다.

수익 관리는 `결제 그룹 수 × 실제 평균 월 매출`에서 PG 수수료·세금·환불·인프라·문의 대응 비용을 뺀다. 사용자 수만으로 이익을 예측하지 않는다.

## 비용의 단계별 기준

2026-09-26 조사 기준. **Nest API 서버 비용을 DB/Auth 비용에 더해야 한다.** 기존 v0.1의 $25/$45/$75는 Supabase 부분 금액이며 Nest 도입 후 전체 운영비가 아니다. 아래 `A`는 서비스별 API 인스턴스 월 비용이다. Render 요금 페이지에는 512MB 컴퓨트 $7/월 항목이 있으므로 `A=$7`을 계산 예시에 사용하지만, 실제 선택 가능한 상품·workspace 요금·자원 적합성은 가입 전 확인한다. [공식 요금](https://render.com/pricing).

| 단계 | DB/Auth + API 월 계산 | A=$7일 때 예시와 전제 |
|---|---:|---|
| 로컬 개발/개인 시험 | 추가 클라우드 비용 $0 가능 | 기존 PC·인터넷, 런타임 사용 조건 충족 |
| 한 서비스 공개 데모 | 무료 한도에서 인프라 $0 가능 | Supabase 무료 슬롯 + Render Free + 정적 호스팅. 실제 운영 수준과 다름 |
| 한 서비스 Pro 운영 | $25 + A | 약 $32, Micro DB 1개 + API 1개 |
| 한 서비스 운영 + 별도 staging | $35 + 2A | 약 $49, DB 2개 + API 2개 |
| 세 서비스 운영 | $45 + 3A | 합계 약 $66, DB/API 각 3개 |
| 세 서비스 운영 + 각각 staging | $75 + 6A | 합계 약 $117, DB/API 각 6개 |

낮은 자원으로 시작할 때의 조건부 계산 예시다. API 메모리/CPU와 동시 처리량은 실제 부하 시험으로 확인하고 부족하면 A를 올려 다시 계산한다. 도메인·메일/CI/스토리지/트래픽 초과·workspace 추가 요금·PG 수수료·세금·AI 구독·노동 비용은 별도다. 무료 staging으로 대체하면 비용은 낮아지지만 운영 환경과 다른 조건을 기록한다.

Render Free는 15분 무요청 시 중지되며 workspace 단위 월 750시간을 공유한다. 세 API를 모두 항상 무료로 실행한다고 가정하지 않는다. 공식 문서도 production 사용을 권하지 않는다. 정시 알림은 서버가 잠들면 지연될 수 있으므로 유료화 여부와 별개로 운영 수준을 선택한다. [무료 조건](https://render.com/docs/free).

Supabase는 무료 활성 프로젝트를 2개까지 제공한다. 기존 계정의 다른 프로젝트 사용 여부는 아직 확인하지 않았다. 세 서비스 모두에 무료 전용 운영 DB를 동시에 준다는 계획은 성립하지 않는다. Pro 계산은 `조직 $25 + Micro 수 × 약 $10 − 컴퓨트 크레딧 $10`이며 실제 시간/사용량에 따라 청구가 달라진다. [공식 계산 예시](https://supabase.com/docs/guides/platform/billing-faq).

Cloudflare 정적 자산 요청은 무료지만 동적 Worker·다른 제품 사용은 별도다. 초기 구성은 정적 배포만 사용한다. [요금](https://developers.cloudflare.com/workers/platform/pricing/). Vercel Hobby는 개인 비상업용 조건이 있어 무료 상용 운영안으로 사용하지 않는다. [조건](https://vercel.com/docs/plans/hobby).

무료 Supabase의 비활성 중지와 관리형 복구 제약을 고려해, 돈을 받거나 중요한 고객 데이터를 맡는 시점에는 매출 발생 여부와 별개로 운영 예산을 검토한다. 무료 백업을 약속하지 않는다. [운영 안내](https://supabase.com/docs/guides/deployment/going-into-prod), [백업](https://supabase.com/docs/guides/platform/backups).

메일 후보 Resend Free는 현재 월 3,000건/일 100건, 도메인 3개를 제시한다. 세 서비스가 한 계정을 쓰면 발송량을 합산해 관리한다. 실제 발신 도메인 구매와 인증, 메일 유형별 한도는 별도 확인한다. [요금](https://resend.com/pricing). 기본 Supabase SMTP를 일반 사용자용으로 그대로 출시하지 않는다. [SMTP 제약](https://supabase.com/docs/guides/auth/auth-smtp).

비용 정책: 먼저 로컬로 만들고 한 서비스만 외부 시험한다. 신규 유료 공급자·용량 업그레이드는 실제 예상 청구액을 정한 뒤 진행한다. 알림이 모든 과금을 자동 차단한다고 가정하지 말고 제품별 spending control 적용 범위를 확인한다. 유료 전환 전 운영 한 달 비용을 매출 없이 감당할 수 있는지가 미결 결정이다.

## 유료화 구현 공통 순서

1. 실제 반복 사용과 지불 의향부터 확인한다. 무료 사용만으로 매출 가능성을 확정하지 않는다.
2. Nest API의 `entitlements`로 기능/용량 권한을 관리한다. UI 플랜 표시는 권한의 기준이 아니다.
3. 한국 우선이므로 토스페이먼츠 결제창/빌링을 우선 검토한다. 실제 사업자 소재지·계약 가능 여부·심사·수수료가 확인되기 전 PG를 확정하지 않는다. 캐나다 거주 여부만으로 한국 가맹 계약 가능 여부를 추정하지 않는다.
4. 테스트 모드에서 주문 금액 서버 결정→결제 결과 검증→구독 권한 반영→실패 재시도→해지/환불을 구현한다. 원문 카드 정보를 직접 수집하는 API 방식은 MVP에서 사용하지 않는다.
5. `구독 주체 + 결제 기간` 유일 키와 PG 멱등키를 사용한다. 타임아웃은 실패로 단정해 새 결제를 만들지 않고 조회/대사로 결과를 확인한다. 중복·역순 웹훅을 처리하고 주기적 대사를 추가한다.
6. 자동결제의 성공이 항상 웹훅으로 온다고 가정하지 않는다. 선택한 PG의 응답/이벤트 명세에 맞춰 처리한다. 구독 해지는 다음 갱신을 중단하고 결제된 기간의 권한 처리는 약관과 일치시킨다.
