# 일정·계좌·카드·이체 통합 가계부 설계안

작성일: 2026-09-26. 상태: 사용자 방향에 따라 계좌·카드·이체까지 확장한 설계 초안. 이후 [F-001 통합 시안](14_UNIFIED_SCREEN_PREVIEW.md)을 작성하고 가상 데이터 동작을 확인했다. 실제 앱·API·금융 원장은 아직 미구현이다.

## 사용자 제안과 범위

사용자는 하나의 캘린더에서 등록할 내용을 `일정` 또는 `가계부`로 선택하고, 각 내역을 캘린더 구성원에게 공유하거나 본인만 볼 수 있게 하는 방향을 제시했다. 색상 구분도 원한다. 이 방향을 다음 화면 설계의 기준으로 삼는다.

사용자는 후속 메시지에서 **계좌·카드·이체를 포함한 가계부도 Dayjoin 안에서 제공하는 방향**을 제시했다. 이전의 단순 수입·지출만 제공하자는 제안을 대체한다. 통합 제품 범위에는 계좌/현금 잔액, 카드 사용·납부, 내부 이체, 수입·지출, 수정·취소·환불, 기간 합계와 기록별 공유를 포함한다.

입력은 먼저 원화 수동 등록으로 구현하는 프로젝트 제안이다. 금융기관 자동 연동·실제 송금/카드 결제 실행은 별도 기능이며 이번 요청만으로 포함시키지 않는다. 계좌와 카드 기능 자체를 후속 서비스로 미루지 않는다. 기존 Cashjoin의 계산·원장 요구사항은 설계 참고로 활용하되, 저장소·DB·Auth·배포의 병합이나 Cashjoin 중단은 결정하지 않았다.

## 등록 흐름

`+ 등록 → 일정 / 가계부 선택 → 내용 입력 → 공개 범위 확인 → 저장`

| 선택 축 | 선택지 | 의미 |
|---|---|---|
| 등록 종류 | 일정 / 가계부 | 필요한 입력 필드를 바꿈 |
| 가계부 구분 | 수입 / 지출 / 이체 / 카드 납부 | 금액의 성격과 잔액·합계 반영 방식을 구분 |
| 공개 범위 | 나만 보기 / 캘린더에 공유 | 누가 해당 내역을 읽을 수 있는지 결정 |
| 공유 대상 | 권한 있는 캘린더 | 해당 캘린더를 볼 수 있는 멤버에게 공개 |

- 일정: 제목, 시작·종료, 종일, 메모. 기존 날짜/시간 검증 유지.
- 가계부 공통: 거래 종류, 제목, 날짜, 양수 금액(KRW), 메모, 공개 범위. 지출을 음수로 입력하게 하지 않는다.
- 수입/지출: 입금 계좌 또는 결제 수단, 수입/지출 분류. 이체: 보내는 계정과 받는 계정. 카드 납부: 출금 계좌와 납부할 신용카드. 선택한 종류에 필요한 필드만 표시한다.
- 계좌·카드 화면: 계정 별칭, 유형, 시작 잔액/미납금과 현재 기록상 잔액. 실제 금융기관 잔액을 실시간 확인한 값처럼 표시하지 않는다.
- 일정을 만들지 않고도 가계부 내역을 등록할 수 있다. 일정과 지출을 연결하는 기능은 별도 후속 선택이다.
- 공개 범위는 저장 버튼 근처에도 `나만 볼 수 있어요` 또는 `우리 둘 캘린더의 멤버에게 보여요`로 표시한다. 처음 등록하는 가계부는 나만 보기를 기본으로 제안한다.

## 같은 화면에서 개인·공유 내역 보기

| 예시 | 종류·표시 | 작성자 화면 | 다른 캘린더 멤버 화면 |
|---|---|---|---|
| 저녁식사 약속 | 일정 · 공유 | 표시 | 표시 |
| 저녁식사 60,000원 | 지출 · 공유 | 표시 | 표시 |
| 개인 선물 30,000원 | 지출 · 나만 보기 | 표시 | 존재·금액·제목 모두 표시하지 않음 |

통합 화면은 본인만의 내역과 선택한 캘린더의 공유 내역을 함께 보여준다. `전체 / 일정 / 가계부`와 `전체 / 나만 보기 / 공유`로 구분해서 볼 수 있도록 제안한다. 다른 멤버의 개인 내역은 같은 날짜에 있어도 포함되지 않는다.

개인 기록은 기존 ADR-D01의 개인 작업 공간 격리를 유지하고, 화면에서 공유 기록과 함께 조회한다. 금융 원장은 개인 장부에 남겨 두고 선택한 거래의 공개용 정보를 캘린더에서 보여주는 구성을 제안한다. 공개 여부가 거래의 소유권이나 잔액 반영 여부를 바꾸지 않는다. 탈퇴나 그룹 삭제는 캘린더 공유 연결을 정리하되 개인 원장·계좌 기록을 삭제하지 않는다. 구체적인 schema는 아직 결정하지 않았다.

첫 버전의 멤버 권한은 기존 그룹 단위를 유지하므로 같은 그룹 내 캘린더는 동일 멤버를 공유한다. 캘린더마다 별도 멤버를 초대하는 기능까지 확정한 것은 아니다. 화면의 공유 대상은 명시한 캘린더이며 다른 그룹 전체나 서비스 전체 공개가 아니다.

## 공개 범위와 집계 규칙

- 나만 보기: 작성자 본인만 조회·수정·삭제. 그룹 관리자도 다른 사람의 개인 기록에 접근하지 못한다.
- 공유: 해당 캘린더를 볼 수 있는 멤버가 조회. 공유 등록은 editor/owner에게 허용하는 초안이며 viewer도 자기 개인 기록은 작성할 수 있다.
- 개인/공유 여부는 서버와 DB의 권한 경계에서 확인한다. 개인 내역을 내려받은 뒤 화면에서 숨기는 방식으로 구현하지 않는다.
- 개인 내역은 타인의 검색·건수·기간 합계·알림·내보내기에도 포함되지 않는다. 탈퇴 후에는 새 조회에서 공유 내역 접근이 차단되어야 한다.
- 공유 지출은 하나의 기록으로 계산한다. 멤버 수만큼 합산하지 않으며, 공동 지출을 각 사람의 실제 개인 부담금으로 간주하지 않는다.
- 합계는 `내 장부의 전체 지출`(내 비공개+내 공유 거래)과 `공유 캘린더의 지출`(보이는 멤버들의 공유 거래)로 구분한다. 비공개 필터 결과는 `나만 보기 지출`로 표시한다. 내 공유 거래가 두 보고서에 나타날 수 있으므로 두 합계를 더해서 내 지출로 표시하지 않는다.
- 공개 범위 변경은 본인 작성 기록에 한해 허용하는 초안이다. 공유로 바꿀 때 대상·공개될 내용을 안내하고, 개인으로 바꿀 때 이후 조회·집계에서 제외한다. 이미 열람·내보낸 사본까지 회수한다고 약속하지 않는다.
- 개인 금융 거래는 원장 소유자만 수정·취소한다. 공유 캘린더의 owner/editor도 다른 사람의 원장·잔액을 바꾸지 못한다. 캘린더 owner는 해당 캘린더에서 공유를 해제할 수 있고 원장 거래는 보존한다. 이는 프로젝트 권한 제안이다.
- 공유 대상이나 공개 여부 변경은 개인 원장 합계와 잔액에 영향을 주지 않는다. 거래 수정·취소 시 공개 화면도 같은 유효 거래 상태를 반영한다.

## 거래 공유와 계좌 정보의 구분

예: 내 신용카드로 결제한 저녁식사 60,000원을 공유하면 캘린더에는 날짜·제목·금액·분류·공개 메모와 작성자를 표시한다. 계좌/카드의 내부 ID, 번호, 별칭, 잔액, 미납금, 한도, 다른 거래, 비공개 수정 이력을 함께 노출하지 않는다. 공개 필드는 서버 응답에서 명시적으로 선택한다. 같은 선택 필드만 검색·알림·내보내기에 사용한다.

이체를 공유해도 양쪽 개인 계정 정보는 자동 공개하지 않는다. 원장 소유자는 계정 이름을 보고, 다른 멤버는 `이체`와 공개 제목·금액을 본다. 원장 ID를 얻거나 추측해 직접 요청해도 별도 원장 권한이 없으면 접근할 수 없어야 한다.

계좌 잔액 자체를 함께 관리하는 공동 장부는 별도 권한 설계다. 일정/거래를 공유했다는 이유로 개인 계좌 전체를 공동 계좌로 바꾸지 않는다.

## 계좌·카드·이체 계산 규칙

| 동작 | 잔액 변화 | 수입·지출 합계 |
|---|---|---|
| 계좌/현금 시작 잔액 | 시작 자산 반영 | 수입에 포함하지 않음 |
| 신용카드 시작 미납금 | 시작 부채 반영 | 이번 달 지출에 포함하지 않음 |
| 수입 | 선택한 자산 계정 증가 | 수입 증가 |
| 현금/계좌 지출 | 선택한 자산 계정 감소 | 지출 증가 |
| 체크카드 사용 | 연결한 은행 계좌 감소 | 지출 1회 반영, 카드 부채 생성 없음 |
| 신용카드 사용 | 해당 카드의 미납금 증가 | 사용일에 지출 1회 반영 |
| 내 계정 간 이체 | 보내는 계정 감소 + 받는 계정 증가 | 수입·지출 모두 제외 |
| 카드 대금 납부 | 출금 계좌 감소 + 카드 미납금 감소 | 지출 추가 없음 |
| 환불 | 원 결제 수단에 금액 반환 | 환불일 순지출 감소 |

내 계정 간 이체는 동일 장부·동일 통화의 서로 다른 계정 사이에서만 제공한다. 양쪽 계정이 등록되어 있어야 하며 타인에게 지급한 식사비·회비 등을 자동으로 내부 이체로 분류하지 않는다. 이체/납부 수수료가 있으면 별도 지출로 기록한다. 계좌·카드의 음수 잔액을 일괄 거부하지 않고 부족 잔액·선납 상태를 구분한다.

환불은 원거래와 연결하고 누적 환불액이 원거래를 넘지 않도록 검증한다. 카드 납부 후 환불로 미납금이 음수가 되면 선납금으로 표시한다. 환불의 공유 기본값은 원거래의 현재 공개 범위를 따르되 저장 전에 확인 가능하게 한다. 공유 합계는 공개된 거래만의 합계이므로 비공개 거래에서 계산한 전체 순액을 공개 화면에 전달하지 않는다.

계좌·카드 정보와 거래는 사용자가 기록한 값이다. 납부 예정 안내만으로 잔액을 차감하지 않으며, 실제 납부를 기록한 거래와 구분한다. 할부 배분·자동 결제 예정액 산출·외화 환산은 별도 세부 범위로 남긴다.

## 원장 구현 기준안

기존 Cashjoin 기획의 원장 검증 규칙을 Dayjoin의 가계부 모듈에 적용하는 프로젝트 선택이다. 사용자에게 분개 입력을 요구하지 않는다.

- 일정과 금융 거래는 구별된 모델로 유지하고 통합 캘린더 조회에서 합친다. 날짜와 공개 범위가 같아도 금융 거래를 일반 일정의 금액 필드 하나로 표현하지 않는다.
- 단일 Nest 애플리케이션 안에서 원장, 계정, 거래 명령과 캘린더 공유 조회의 책임을 구분한다. 필요할 때 공식 CLI로 생성하며 빈 모듈·공통 금융 서비스부터 만들지 않는다.
- 내부 원장은 균형 잡힌 분개를 기준으로 잔액을 유도한다. 원화 정수·금액 범위를 검증하고 정확한 합계를 유지하며, API의 금액 문자열과 서버 계산 경로를 명세한다.
- 이체의 양쪽 반영, 카드 납부, 수정·취소·환불과 공개 화면 반영은 DB 트랜잭션으로 처리한다. 실패 시 부분 잔액이나 일부 공개 변경이 남지 않아야 한다.
- 게시된 원장을 직접 덮어쓰지 않고 수정/취소 이력을 보존한다. 같은 요청 재전송은 한 번만 기록하고 동시 수정·동시 환불 충돌을 검증한다.
- 원장 권한과 캘린더 열람 권한을 별도로 확인하며 개인 금융 원장에는 개인 소유 경계를 적용한다. 실제 금융 데이터로 시험하기 전에 두 사용자 권한 시험을 통과한다.

## 숫자로 확인할 인수 예시

같은 개인 장부, 수수료 없음, 모든 동작이 같은 보고 기간에 있다는 시험 조건이다. 실제 사용자 거래가 아니다.

| 순서 | 은행 A | 은행 B | 카드 미납금 | 누적 순지출 |
|---|---:|---:|---:|---:|
| A 시작 잔액 100,000원 | 100,000 | 0 | 0 | 0 |
| A에서 B로 20,000원 이체 | 80,000 | 20,000 | 0 | 0 |
| 카드로 식사비 60,000원 사용 | 80,000 | 20,000 | 60,000 | 60,000 |
| A에서 카드 대금 60,000원 납부 | 20,000 | 20,000 | 0 | 60,000 |
| 카드로 10,000원 부분 환불 | 20,000 | 20,000 | −10,000(선납) | 50,000 |

식사비를 공유하거나 비공개로 바꿔도 위 개인 잔액과 순지출은 동일해야 한다. 공유 시 다른 멤버에게는 선택한 식사비/환불 정보만 보이고 위 계정별 잔액은 보이지 않아야 한다.

## 색상과 표시 제안

| 종류 | 포인트 색 제안 | 색 이외의 표시 |
|---|---|---|
| 일정 | 부드러운 라벤더 | 캘린더 아이콘 + 일정 |
| 지출 | 살구/테라코타 | 지출 문구 + `−60,000원` |
| 수입 | 차분한 블루 | 수입 문구 + `+100,000원` |
| 이체·카드 납부 | 중립 회색 | 이동 아이콘 + 거래 종류, 수입·지출 제외 문구 |

아이보리·따뜻한 차콜 바탕과 둥근 형태는 ADR-D06을 유지한다. 색상은 기록 종류를 나타내고, 공개 범위는 `자물쇠 + 나만 보기`, `사람 아이콘 + 캘린더 이름`으로 구분한다. 종류·공개 범위·그룹을 모두 색 하나에 중복해서 맡기지 않는다. 이 초안에서는 기존 그룹별 색 계획보다 기록 종류의 색을 우선하며 그룹은 이름으로 구분한다. 정확한 색과 대비는 후속 시안에서 검증한다.
